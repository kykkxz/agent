# 一、RAG核心概念和工作流程

## 1.RAG是什么？

检索增强生成：检索外部文档信息，结合大模型生成答案，核心解决了大模型的两个痛点：

- 知识过时：大模型的训练数据有限，无法获取最新的信息

- 幻觉问题：大模型会编造一些不存在的信息

核心结论：RAG本质是一条特殊的Chain，"检索-拼接提示词-模型生成-解析"固定的流水线，无自主思考能力，不属于agent。

## 2.RAG 与 Chain、Agent 的区别

| 组件    | 核心特点               | 适用场景              |
| ----- | ------------------ | ----------------- |
| Chain | 固定流程，无检索、无工具调用     | 简单文本任务（翻译、文案）     |
| RAG   | 固定流程，包含“检索外部文档”步骤  | 知识库问答（如招聘、文档咨询）   |
| Agent | 动态决策，自主调用工具（可包含检索） | 复杂多步骤任务（查数据库\+检索） |

如果把检索作为一个工具，那么RAG就可以看作是Agent的一个组件。

## 4.RAG 核心工作流程

![28d7bece-7793-4445-abd7-5c568bc0f37f](file:///C:/Users/qiuxingyu/OneDrive/Pictures/Typedown/28d7bece-7793-4445-abd7-5c568bc0f37f.png)

RAG分为两大阶段：构建阶段（离线准备）和检索阶段(在线回答)，全程是固定流水线，对应一条chain。

##### （1）构建阶段：离线准备，只需要做一次

- 1.文档加载（解析）：加载外部文档（如pdf招聘简章，word文档）

- 2.文档拆分chunk:将长文档拆分成短文本片段chunks，避免大模型上下文不足，避免过多无关内容干扰；

- 3.Embedding编码：将每个文本片段转化为向量，捕捉文本语义信息（多模态RAG）；

- 4.向量存储：将向量存入向量数据库（如Chroma）,方便后续检索。

##### (2)检索阶段：在线回答，每次用户提问都会执行

- 1.用户提问：用户输入的问题（”java的岗位要求是什么？“）

- 2.问题编码：将用户问题转为向量

- 3.相似检索：在向量数据库中，检索与问题最相关的top-k文本片段（3，5，10）

- 4.Prompt拼接：将检索的文本片段（上下文）与用户问题，提示词拼接；

- 5.模型生成：大模型结合上下文，也就是将拼接好的promt作为输入生成准备回答（不编造信息）；

- 6.输出解析：将回答解析为清晰的格式，返回给用户。

##### （3）打个比方

- 构建阶段：把参考书拆成知识点卡片，存入大脑（向量数据库）

- 检索阶段：遇到用户提问，先大脑中提取知识卡片，再结合问题回答，不瞎编。

#### （2）文档拆分策略

为什么要拆分？大模型上下文限制；片段语义集中，检索更精准。

#### 常用拆分策略

- 按字符长度拆分：固定每个片段的字符数（200字一个chunck），简单粗暴，拆分到句子中间，破坏语义

- 按标点符号的语义拆分（推荐）：用 RecursiveCharacterTextSplitter，按句子、段落拆分，避免破坏语义，拆分后片段更连贯；

- 按标题拆分：按文档中的标题，适合结构清晰的文档
  
  

Langchain中的RecursiveCharacterTextSplitter 与 CharacterTextSplitter

```python
from langchain_text_splitters import (
    CharacterTextSplitter,
    RecursiveCharacterTextSplitter
)

raw_text = """人工智能技术如今正在渗透各行各业，从日常的聊天助手、图片生成工具，再到工业质检、医疗问诊、智能交通等落地场景，大模型已经成为数字化转型当中不可或缺的底层能力。
很多企业在搭建知识库问答、内部文档RAG系统的时候，最先遇到的难题便是文档切片。切片质量直接决定后续向量检索、答案召回的准确度。

如果整块文本过长，一块里面混杂多个主题，用户提问时很容易检索到无关内容；
如果分块太短，语义被强行割裂，上下文信息丢失，大模型就很难读懂完整语境。

字符分割器只会按照指定分隔符进行切割，当段落长度超过chunk‑size之后不会再次细分；
递归字符分割器会依照优先级依次尝试换行、句号、逗号、空格逐层拆分，更加适合中文散文、技术文档、工作总结这类非结构化材料。

在实际工程实践当中，chunk_size一般根据嵌入模型上下文窗口调整。
普通轻量向量模型适合设置300‑800字符；长文本嵌入模型可以给到1000~2000字符。
chunk_overlap重叠部分主要用来保障两块相邻切片之间语义连贯，避免句子被拦腰切断之后丢失上下文关联。

搭建知识库的时候，除文本分片之外，我们还需要处理PDF、Word、Markdown多种格式加载、清洗多余换行、去除特殊符号、过滤空白片段，之后再送入向量数据库完成向量化存储。
后续用户问题向量化之后，执行相似度检索，取出最相关的文本块交给大模型生成回答，整套流程便是标准的检索增强生成架构。"""


# 普通分割
char_splitter = CharacterTextSplitter(
    separator="",  ##“/n/n”
    chunk_size=100,
    chunk_overlap=10
)

# 递归分割（日常RAG首选）
recur_splitter = RecursiveCharacterTextSplitter(
    separators=["\n\n", "\n", "。", "，", " ", ""], # 适配中文分隔符
    chunk_size=300,
    chunk_overlap=30
)

chunks1 = char_splitter.split_text(raw_text)
chunks2 = recur_splitter.split_text(raw_text)
print(len(chunks1[0]))
```

# 三、RAG进阶/优化

在基础rag流程(加载数据-分块-embedding编码-向量库；embedding-向量检索-Prompt拼接-llm生成)实现，优化目标：

提升检索精度，减少冗余信息

## 1.分块策略优化：自主构建textspliter

（1）常见的分块方法：固定长度，递归切分（固定的规则），语义切分（不固定的长度和不固定的规则），特殊文本（md，html等）专业切分工具

（2）分块大小动态调整：动态调整分块大小，避免“大文档分块过细导致信息碎片化”或”小文档过粗导致冗余“

- 高密度文档：技术文档，规章制度，分块长度200-300字符，确保每一块分块聚焦一个知识点

- 低密度文档：通知，公告，分块长度设置大一些500-500字符，避免分块过细

- 添加”重叠长度“：避免相邻分块的予以断裂

（3）分块元数据优化

数据的元数据：描述数据特征的数据。分块增加丰富的元数据（比如文档名称，章节标题，页面，主题标签等），检索的时候将元数据的内容作为检索的限制条件，进一步缩小检索范围。

举例：

给“员工年假规定”的分块增加元数据（“source”：“员工手册”，“chapter”：“员工福利”，“page”：15），提问“员工手册中关于年假的规定”，检索系统优先找到“员工手册”标签的分块。

（4）**parent-child分块**：子分块用来检索，父分块用来拼接。适用于高密度文档。 子分块不能完整回答问题，其父分块（加上前前后后更多的文本块）涵盖信息更多，更全面。

## 2. 检索方式优化

### （1）稠密检索+稀疏检索：根据文本块类别，调整权重配比

- embedding相似检索：通过向量形似度排序找出最相似的前k个分块

- 稀疏检索（BM25）：通过提取核心关键词，在向量库的元数据或者分块内容中，精确匹配这些关键词

补充知识：

TF-IDF算法=词频x逆文档频率，经典的关键次权重蒜贩，早期的搜索引擎相关性打分基础，也是BM25的前身。

TF：词频，词语在当前文档出现了多少次

IDF：逆文档频率，衡量一个词语的稀有程度，某一个词能多大代表一个文档

一共有1000篇文档：

950篇都带有“人”：idf就很低

10篇“蝾螈”：idf很高，专属关键词

TF-IDF算法=词频x逆文档频率

文档库100个分块，分块A里面“区块链”5次，100个分块只有5个分块含有“区块链”

TF=5

IDF=ln（100/5) =ln20 越等2.996

TF-IDF =14.98 “区块链”这个词可以代表这个文档的指数

BM25做了一个超长文档的惩罚因子，使得长文档不会因为长度获得高的tf-idf

qurey中的词进行分词，之后每个词对应去算每个文本块的bm25，然后加成起来最高的那个文档就是稀疏检索最高得分最相似的文本块
